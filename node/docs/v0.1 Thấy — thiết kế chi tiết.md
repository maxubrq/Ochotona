## Kiểu dữ liệu lõi

CL2 và CL4 được cưỡng chế ở tầng kiểu: một giá trị đọc từ broker không bao giờ là `T` trần, mà là `Observed<T>`, và trạng thái `unknown` mang lý do có cấu trúc. Luật không thể vô tình coi "không đọc được" là "bằng 0".

```ts
// @ochotona/model/observed.ts
export type SourceId = 'http.list' | 'http.stats' | 'prometheus' | 'snapshot';

export type Observed<T> =
  | { state: 'known';   value: T; source: SourceId; path: string; observedAt: string }
  | { state: 'unknown'; reason: UnknownReason; source: SourceId; path: string };

export type UnknownReason =
  | { kind: 'source_unavailable' }               // thống kê tắt, Prometheus đóng
  | { kind: 'forbidden'; status: 401 | 403 }      // user thiếu quyền
  | { kind: 'endpoint_missing'; status: 404 }     // phiên bản không có endpoint
  | { kind: 'field_absent' }                      // endpoint có, trường không có
  | { kind: 'model_mismatch' }                    // CLI tính khác broker
  | { kind: 'tie' }                               // hai policy cùng priority
  | { kind: 'regex_unsupported' }
  | { kind: 'error'; message: string };
```

```ts
// @ochotona/model/actual.ts (rút gọn)
export interface Actual {
  broker: {
    version: Observed<string>;
    metadataStore: Observed<'mnesia' | 'khepri'>;
    nodes: Observed<NodeInfo[]>;            // phiên bản, mem_limit, disk_free_limit
    featureFlags: Observed<Record<string, 'enabled' | 'disabled'>>;
    deprecatedInUse: Observed<string[]>;
    counters: {
      unroutableDropped: Observed<Counter>;
      unroutableReturned: Observed<Counter>;
    };
    sources: Record<SourceId, 'ok' | 'unavailable' | 'forbidden'>;
  };
  exchanges: Exchange[];  queues: Queue[];  bindings: Binding[];
  policies: Policy[];     operatorPolicies: Policy[];
  connections: Observed<Connection[]>;
  channels: Observed<Channel[]>;
  consumers: Observed<Consumer[]>;
  whoami: Observed<{ name: string; tags: string[] }>;
}

export interface Counter { count: number; since: string }  // since = lúc node khởi động

export interface Queue {
  vhost: string; name: string; type: 'classic' | 'quorum' | 'stream';
  durable: boolean; autoDelete: boolean; exclusive: boolean;
  arguments: Record<string, unknown>;
  effective: Observed<Effective>;          // từ policy-match, đã tự kiểm với broker
  consumers: Observed<number>;
  ready: Observed<number>;  unacked: Observed<number>;
  deliverRate: Observed<number>;  redeliverRate: Observed<number>;
}

export type Layer = 'argument' | 'policy' | 'operator_policy' | 'builtin_default';
export type Effective = Record<string, { value: unknown; layer: Layer; by?: string }>;
```

```ts
// @ochotona/rules/types.ts
export type Result = 'fail' | 'pass' | 'not_checked' | 'not_applicable';
export type Severity = 'S1' | 'S2' | 'S3' | 'S4' | 'S5';
export type Tolerance = 'strict' | 'loose' | 'undeclared';

export interface RuleDef<O> {
  code: string;                                    // 'T2'
  appliesTo: 'exchange' | 'queue' | 'channel' | 'consumer' | 'connection' | 'broker';
  requires: FieldPath[];                           // engine dùng để sinh not_checked
  severity(o: O, ctx: Ctx): Severity;              // phụ thuộc dung sai, phiên bản
  evaluate(o: O, ctx: Ctx): Verdict;
}

export type Verdict =
  | { result: 'pass' | 'not_applicable' }
  | { result: 'fail'; evidence: Evidence[]; params: Record<string, string | number> };

export interface Ctx {
  actual: Actual;
  tolerance(o: ObjectRef): Tolerance;              // từ ocho.yaml, hoặc 'undeclared'
  caps: Capabilities;                              // từ bảng năng lực theo phiên bản
  targetVersion?: string;
}
```

`params` lấp vào khuôn câu trong `i18n/<lang>.json`, ví dụ `"T2.what": "{count} unroutable messages dropped since {since}"`. Luật không tự viết câu (CL8), nên dịch không bao giờ lệch nghĩa giữa hai thứ tiếng.

**Phát hiện nguồn.** Ba phép thử chạy song song trong pha nhận diện, mỗi phép có trần 2 giây:

1. `http.list`: `/api/overview` trả 200. Không được thì dừng ở K2, exit 3.
2. `http.stats`: `/api/overview` có khoá `message_stats`. Không có thì mọi trường tốc độ và bộ đếm là `unknown` với lý do `source_unavailable`.
3. `prometheus`: GET `/metrics` trả 200 và dòng đầu đúng định dạng Prometheus; ngắt kết nối ngay sau dòng đầu để không kéo cả payload.

**Kiểm soát tải (CL6).** Token bucket 5 request mỗi giây, tối đa 2 request đồng thời. Một phản hồi chậm hơn 2 giây thì giảm tốc còn một nửa, sàn 1 request mỗi giây; mười phản hồi nhanh liên tiếp thì tăng 1, trần 5. Trước khi kiểm kê, reader tính số trang từ `object_totals`; trên 2.000 queue thì in số request và thời gian ước tính.

**Xử lý lỗi theo mã HTTP.**

| Tình huống | Hành vi |
| --- | --- |
| 401 ở `/api/overview` | Exit 3, nói ba điều, in cách tạo user `monitoring` |
| 401, 403 ở endpoint khác | Trường phụ thuộc thành `unknown: forbidden`; các luật liên quan thành `not_checked`; chạy tiếp |
| 404 | `unknown: endpoint_missing`; chạy tiếp |
| 502, 503, 504, mất kết nối | Thử lại tối đa 2 lần, chờ ngẫu nhiên 0,5 đến 2 giây; vẫn hỏng thì `unknown: error` |
| Quá 15 giây | Như trên |
| Ctrl-C | Huỷ mọi request, in số trang đã đọc trên tổng, exit 130; không in báo cáo nửa vời |

**Ảnh chụp.** `--save` ghi `Actual` thành JSON với `schema: ocho.snapshot/1`. `--from` đọc lại và gắn nguồn `snapshot` cho mọi trường, nên báo cáo luôn cho biết nó chấm trên dữ liệu cũ, kèm thời điểm chụp.

## Khớp policy và tự kiểm

Sáu trong tám luật S1 đọc giá trị hiệu lực của một khoá trên queue hoặc exchange, nên khớp policy sai là sai cả loạt. Vì vậy CLI tự tính giá trị hiệu lực, rồi đối chiếu với chính broker ở mọi chỗ broker cho phép; chỗ nào lệch thì nói "không xác định" thay vì đoán.

**Ba bước tính.**

1. **Chọn policy.** Trong các policy cùng vhost có `pattern` khớp tên và `apply-to` khớp loại đối tượng (`all`, `exchanges`, `queues`, `classic_queues`, `quorum_queues`, `streams`), lấy policy có `priority` cao nhất. RabbitMQ chỉ áp một policy, không gộp khoá giữa các policy (L3). Hai policy cùng priority cao nhất thì kết quả là `unknown: tie`, cho tới khi câu hỏi mở về thứ tự được trả lời.
2. **Gộp operator policy.** Chọn operator policy cùng cách. Với khoá có ở cả hai, khoá số lấy giá trị nhỏ hơn.
3. **Gộp với argument.** Theo bảng dưới, vì quy tắc khác nhau theo từng khoá.

| Khoá | Argument và policy cùng có | Luật đọc |
| --- | --- | --- |
| `alternate-exchange` | Argument thắng | T2 |
| `dead-letter-exchange`, `dead-letter-routing-key` | Argument thắng | T4, T5, T9 |
| `dead-letter-strategy`, `overflow` | Argument thắng | T3, T5 |
| `max-length`, `max-length-bytes` | Giá trị nhỏ hơn | T3 |
| `message-ttl` | Giá trị nhỏ hơn | T9 |
| `delivery-limit` | Giá trị nhỏ hơn | T4 |
| `x-queue-type` | Chỉ có ở argument | T1 |

Bảng này là giả định GC10, kiểm bằng fixture riêng cho từng khoá trên cả ba phiên bản trước khi luật nào dựa vào nó được bật.

**Tự kiểm với broker.** Queue có trường `effective_policy_definition`: đó là kết quả bước 1 và 2 do chính broker tính. CLI so kết quả của mình với trường này cho từng queue. Lệch thì `effective` của queue đó thành `unknown: model_mismatch`, các luật phụ thuộc thành `not_checked`, và cuối báo cáo in một dòng mời gửi ảnh chụp `--save --redact-hosts` vào issue. Đây là cơ chế A13 áp vào chính mô hình của CLI: lỗi của Ocho hiện ra thành "chưa kiểm", không thành phát hiện sai.

Exchange không có trường tương đương, nên với exchange CLI dựa vào trường `policy` (tên policy broker đang áp) để kiểm bước 1.

**Biểu thức chính quy.** Broker dùng regex của Erlang (PCRE), CLI chạy trên RegExp của JavaScript. Phần lớn pattern thực tế (`^`, `$`, `.`, lớp ký tự, `|`, lượng từ) giống nhau. Pattern có cú pháp không chắc tương đương (nhóm nguyên tử, lượng từ chiếm hữu, `\Z`, cờ nội tuyến) thì việc khớp policy đó là `unknown: regex_unsupported`, không dịch gần đúng.

## Bộ máy luật

Người viết luật không được tự xử lý trường hợp "không đọc được": bộ máy làm việc đó trước khi gọi luật. Một luật quên CL2 vì vậy không thể tồn tại.

**Vòng chạy cho mỗi cặp (luật, đối tượng).**

1. Lọc đối tượng theo `appliesTo`, `--vhost`, `--flow`, và danh sách loại trừ hệ thống (dưới).
2. Phân giải từng đường dẫn trong `requires`. Một đường dẫn `unknown` thì kết quả là `not_checked` mang lý do của đường dẫn đó; luật không được gọi.
3. Phân giải `optional`. Đường dẫn `unknown` ở đây không chặn luật, chỉ làm thiếu bằng chứng; luật nhận `null` và tự hạ mức nếu cần.
4. Gọi `severity` rồi `evaluate`.
5. Áp miễn trừ từ `ocho.yaml`: phát hiện vẫn là `fail`, gắn `waiver`, đếm riêng, không làm exit 1. Miễn trừ quá `until` thì không có hiệu lực, kèm một phát hiện S3 "waiver expired".

**Kiểu bảo đảm điều đó.** `requires` khai dạng `as const`; hàm `evaluate` nhận một khung nhìn trong đó các trường đã khai là giá trị trần, các trường khác vẫn là `Observed`. Đọc một trường không khai trong `requires` mà không xử lý `unknown` thì không biên dịch được.

```ts
export const T5 = defineRule({
  code: 'T5',
  appliesTo: 'queue',
  requires: ['type', 'effective'] as const,
  optional: [] as const,
  severity: () => 'S1',
  evaluate(q) {
    if (q.type !== 'quorum') return { result: 'not_applicable' };
    const dlx = q.effective['dead-letter-exchange'];
    if (!dlx) return { result: 'not_applicable' };          // không dead-letter: việc của T4
    const strategy = q.effective['dead-letter-strategy']?.value ?? 'at-most-once';
    const overflow = q.effective['overflow']?.value ?? 'drop-head';
    if (strategy === 'at-least-once' && overflow === 'reject-publish') return { result: 'pass' };
    return { result: 'fail',
             evidence: [layerOf(q, 'dead-letter-strategy'), layerOf(q, 'overflow')],
             params: { strategy: String(strategy), overflow: String(overflow) } };
  },
});
```

**Loại trừ hệ thống, áp cho mọi luật trừ khi luật ghi khác.**

| Đối tượng | Lý do |
| --- | --- |
| Exchange mặc định `""` và `amq.*` không có binding | Không mang luồng nào |
| Queue `exclusive`, queue tên `amq.gen-*` | Queue tạm của một connection, không giữ custody |
| Queue `mqtt-subscription-*` | Thuộc T11, T12; ngoài phạm vi v0.1, báo `not_applicable` kèm ghi chú |
| Queue `ocho.*` | Đối tượng hệ thống của Ocho, có luật riêng về sau |

**Tất định.** Cùng `Actual` và `ocho.yaml` thì JSON đầu ra giống từng byte: sắp theo mức, mã luật, vhost, tên; thời điểm chỉ lấy từ `observedAt`, không gọi đồng hồ trong luật. Snapshot test dựa vào điều này.

**Chỉ mục dựng một lần.** Binding theo exchange nguồn, consumer theo queue, channel theo connection. Mọi luật chạy trong O(số đối tượng); broker 10.000 queue chấm xong dưới 1 giây sau khi đọc.

## Tám luật S1

Mỗi luật dưới đây có điều kiện `fail` viết thành vị từ, quy tắc chọn mức, và ít nhất một mẫu gần giống phải `pass`; fixture dựng thẳng từ bảng này. "Dung sai" là dung sai của luồng chứa đối tượng, lấy từ `ocho.yaml`, mặc định `undeclared`.

| Luật | `fail` khi | Mức | Mẫu gần giống phải `pass` |
| --- | --- | --- | --- |
| T2 | Exchange có ít nhất một binding đi ra, và `alternate-exchange` hiệu lực vắng, hoặc trỏ tới exchange không tồn tại, hoặc trỏ tới exchange không có binding nào | `strict`: S1. `undeclared`: S1 nếu bộ đếm unroutable bị bỏ > 0, còn lại S3 | Alternate exchange đặt qua policy; alternate exchange là fanout có queue |
| R1 | Channel có `publish` > 0 và `confirm` = false | S1 khi `ocho.yaml` gán user của connection cho một luồng `strict` (khối `services`); còn lại S3 | Channel chỉ consume; channel có confirm |
| C1 | Consumer có `ack_required` = false trên queue không bị loại trừ | Theo dung sai của queue: S1, hoặc S3 khi `undeclared` | Consumer trên direct reply-to (`amq.rabbitmq.reply-to` bắt buộc không ack) |
| T1 | Queue `classic`, `durable`, không `exclusive`, không `auto_delete` | `strict`: S1. `undeclared`: S3 khi có consumer và có message; còn lại `pass` | Quorum queue; classic `exclusive` |
| T5 | Quorum queue có `dead-letter-exchange` hiệu lực, và không đồng thời có `dead-letter-strategy: at-least-once` với `overflow: reject-publish` | S1 | Đủ cả hai khoá, đặt qua policy |
| T4 | Quorum queue không có `dead-letter-exchange`, và có đường bỏ message: `delivery-limit` đặt rõ, hoặc broker ≥ 4.0 (mặc định 20) | S1 | Có dead-letter at-least-once và `delivery-limit` 10 |
| T4 (biến thể) | Trên 3.13: quorum queue không đặt `delivery-limit` | S3: không mất, nhưng message độc giao lại vô hạn và chặn queue | Như trên |
| T3 | `max-length` hoặc `max-length-bytes` hiệu lực, và `overflow` là `drop-head` (giá trị mặc định khi không đặt) | `strict`: S1. `undeclared`: S3 | `overflow: reject-publish`; `reject-publish-dlx` |
| T9 | `message-ttl` hoặc `expires` hiệu lực, và không có `dead-letter-exchange` | `strict`: S1. `undeclared`: S3 | TTL kèm dead-letter at-least-once |

Ba cơ chế cần in nguyên văn trong trường `mechanism`, vì đó là chỗ người giỏi vẫn sai:

- **T2:** broker vẫn gửi confirm cho message bị bỏ vì không định tuyến được. Publisher có confirm vẫn không biết mình mất message.
- **T5:** đặt `at-least-once` mà thiếu `reject-publish` thì broker lặng lẽ quay về `at-most-once`. Cấu hình trông đúng, hành vi vẫn là có thể mất (giả định GC11).
- **T9:** `expires` xoá cả queue khi queue không có consumer trong khoảng thời gian đó, kéo theo mọi message còn trong queue, không qua dead-letter.

Khối `services` trong `ocho.yaml` dùng cho R1 là bổ sung của v0.1: nó nối user RabbitMQ với các luồng của service, đúng với Q1 của spec vốn đã sinh một user cho mỗi service.

## Báo cáo và ba việc làm trước

Báo cáo văn bản được viết để đọc trong 60 giây: S1 đầy đủ, S2 và S3 rút gọn, S4 và S5 mỗi luật một dòng, và kết bằng ba việc. JSON luôn đầy đủ.

**Thứ tự khối trong báo cáo văn bản.**

1. Đầu báo cáo, ba dòng: kết nối, phiên bản và metadata store, nguồn dữ liệu.
2. S1: mỗi phát hiện đủ năm trường (chuyện gì, dữ liệu có an toàn không, làm gì tiếp, bằng chứng, cơ chế).
3. S2, S3: bốn trường, bỏ cơ chế; `--why` hiện lại.
4. S4, S5: một dòng mỗi luật, dạng `C2 ×5 queues`; `--verbose` mở ra.
5. Chưa kiểm: nhóm theo lý do, mỗi nhóm một dòng kèm cách mở khoá ("enable the Prometheus plugin to check 3 more S1 rules").
6. Điểm mù: một dòng cố định nêu 9 lỗi không lộ ra từ broker và chỗ sẽ bắt chúng (`lint`, client).
7. Ba việc làm trước.
8. Dòng đếm và exit code.

**Thuật toán chọn ba việc.**

1. Gom các phát hiện `fail` chưa được miễn theo cặp (luật, kiểu sửa) thành hành động; một hành động phủ nhiều đối tượng.
2. Chỉ xét S1 đến S3.
3. Sắp theo khoá, lần lượt:
   1. mức nghiêm trọng;
   2. bậc cơ chế, theo trình tự sửa 12.2: mất đã xảy ra (T2 có bộ đếm > 0) trước đường đang bỏ message ngay lúc này (T3, T4, T5, T9) trước đường có rủi ro (T1, C1, R1);
   3. số đối tượng bị ảnh hưởng, nhiều trước;
   4. mã luật, để tất định.
4. Lấy ba hành động đầu. Không có hành động nào thì in "No S1–S3 actions", kèm số luật S1 chưa kiểm nếu khác 0, để "không có gì" không bị đọc thành "an toàn".
5. Mỗi hành động là một câu mệnh lệnh: tối đa ba tên đối tượng rồi "and N more", mã luật, lệnh `ocho explain <mã>`.

**Hợp đồng `ocho.report/1`.**

## `ocho import`

`import` ghi hai lớp vào `ocho.yaml`: lớp ngữ nghĩa (`flows`, `families`, dung sai) do người dùng quyết, và lớp `topology` chép nguyên trạng từ broker. Lớp thứ hai làm cho tự kiểm vòng tròn đúng theo cấu tạo; lớp thứ nhất là thứ doctor cần để chấm chính xác.

**Phạm vi v0.1:** vhost, exchange, queue, binding, policy, operator policy. User và quyền nằm ngoài `ocho.yaml` cho tới v0.3, khi compiler sinh user theo Q1. Nhờ vậy `import` từ broker chạy được bằng user `monitoring`, không cần quyền xuất definitions.

**Bước 1: suy luồng.**

| Trường hợp | Luồng sinh ra | Tên luồng |
| --- | --- | --- |
| Exchange `direct` hoặc `topic`, mỗi binding key khác nhau | Một luồng cho mỗi key; mỗi queue đích là một nhóm consumer | Key nếu có dạng `<domain>.<entity>.<event>`, nếu không thì `<exchange>/<key>` |
| Exchange `fanout` | Một luồng cho exchange | Tên exchange |
| Queue không có binding nào ngoài exchange mặc định | Một luồng `direct:<queue>` | Như vậy; kèm ghi chú: publisher gửi thẳng qua exchange mặc định, nên T2 không áp được và doctor sẽ nói điều đó |
| Đối tượng không thuộc luồng nào | Không có | Liệt kê ở dòng tổng kết là "unmanaged" |

**Bước 2: suy họ topology.** Tách tên theo `.`, `_`, `-`. Gom các tên cùng số token và chỉ khác nhau ở đúng một vị trí. Một nhóm thành đề xuất khi có ≥ 3 thành viên và cùng chữ ký (loại queue, argument, policy hiệu lực). Nếu routing key của các thành viên cũng chỉ khác ở cùng token đó thì đề xuất luôn mẫu routing key. Tham số mặc định tên `{p1}`; người dùng đặt lại tên lúc duyệt.

Ví dụ đúng với hệ thống quét file: `request_clamav_q`, `request_yara_q`, `request_pdf_q` cùng quorum, cùng policy, routing key `request_clamav`, `request_yara`, `request_pdf` → đề xuất họ `request_{p1}_q`, routing key `request_{p1}`, thành viên `[clamav, yara, pdf]`.

**Bước 3: hỏi.** Chỉ khi stdin là terminal; không phải terminal thì tự chuyển sang `--non-interactive`.

```
Found 214 queues, 37 exchanges → 41 flows, 2 family proposals.

Family proposal 1/2: request_{p1}_q  (3 members: clamav, yara, pdf)
  [a]ccept  [r]ename parameter  [s]kip > r
  Parameter name: engine_id

Flow 1/41: scan.request/request_{engine_id}   ~120 msg/s · 3 queues
  strict = a classic queue or a missing alternate exchange here is an S1 finding
  [s]trict  [l]oose  [k]eep undeclared  [A]pply to the rest of this exchange > s
```

Luồng được hỏi theo tốc độ message giảm dần, để luồng quan trọng nhất được quyết khi người dùng còn tỉnh táo; không có thống kê thì theo số queue.

**Bước 4: ghi.**

```yaml
# ocho import 0.1.0 · context prod · 2026-10-04T01:30:00Z
spec: "0.4"
broker: { min_version: "3.13" }

families:
  scan.request:
    exchange: scan.request
    routing_key: "request_{engine_id}"
    queue: "request_{engine_id}_q"
    members: [clamav, yara, pdf]

flows:
  scan.request:
    family: scan.request
    tolerance: strict
  billing.invoice.created:
    exchange: billing
    routing_key: billing.invoice.created
    groups: [billing.invoice.created.email, billing.invoice.created.ledger]
    tolerance: undeclared

topology:            # chép nguyên trạng; v0.1 không sửa lớp này
  queues:
    - { vhost: "/", name: request_clamav_q, type: quorum, durable: true,
        arguments: { x-queue-type: quorum }, flow: scan.request }
  # exchanges, bindings, policies, operator_policies tương tự
```

**Bước 5: tự kiểm vòng tròn.** Biên dịch lớp `topology` thành definitions đã chuẩn hoá (sắp khoá, bỏ trường do broker tự thêm theo bảng chuẩn hoá có fixture) và so với dữ liệu vừa đọc. Lệch dù một trường thì không ghi file, in chỗ lệch, exit 5 vì đó là lỗi của Ocho, không phải của người dùng.

**Import lại khi đã có `ocho.yaml`.** Giữ mọi quyết định của người dùng (dung sai, tên họ topology, tên tham số, miễn trừ, `services`), chỉ làm mới `topology`, và chỉ hỏi luồng mới xuất hiện. In thay đổi topology dạng diff. Không bao giờ ghi đè một dung sai đã khai (A2: hỏi một lần).

## `ocho explain` và `ocho context`

`explain` là chỗ người trực đọc lúc 3 giờ sáng, nên mỗi dòng trả lời đúng một câu "giá trị này từ đâu ra, và đổi được ngay không".

```
$ ocho explain queue request_clamav_q
queue request_clamav_q · quorum · vhost / · flow scan.request (strict)

KEY                   VALUE         LAYER             SET BY                     RUNTIME  NOTE
x-queue-type          quorum        argument          -                          no
dead-letter-exchange  ocho.retry    policy            scan-dlx (prio 10)         yes
dead-letter-strategy  at-most-once  builtin default   -                          yes      T5 S1
overflow              drop-head     builtin default   -                          yes      T5 S1
delivery-limit        10            operator policy   ops-ceiling; policy        yes
                                                      asked 50, lower wins
max-length            100000        policy            scan-dlx (prio 10)         yes

Matching policies:  scan-dlx (prio 10, applied) · catch-all (prio 0, ignored)
Broker agrees:      effective_policy_definition matches (01:22:10Z)
```

Cột `RUNTIME` = đổi được khi đang chạy: khoá đến từ policy thì có, khoá đến từ argument thì không, phải đi đường migration (MG3). Cột `NOTE` nối giá trị với luật đang `fail` vì nó.

**`explain <mã luật>`** chạy không cần mạng: mức và cách chọn mức, vị từ `fail`, cơ chế, mục spec, mục lesson, cách sửa, và chính các mẫu lỗi, mẫu gần giống của fixture làm ví dụ. Fixture vì vậy vừa là test vừa là tài liệu, không thể lệch nhau.

**`explain flow <tên>`** liệt kê đối tượng của luồng, dung sai, các luật áp cho luồng đó và kết quả lần doctor gần nhất nếu có ảnh chụp.

**`ocho context`.** File nằm ở thư mục cấu hình theo chuẩn XDG (Windows: `%APPDATA%`), quyền 0600; quyền rộng hơn thì CLI cảnh báo ở mỗi lần chạy.

```yaml
current: prod
contexts:
  prod:
    url: https://b-1234.mq.ap-southeast-1.amazonaws.com
    user: ocho-doctor
    password_command: "op read op://infra/rabbit-prod/password"
    ca: null
    prometheus_url: null
```

Đây là thay đổi so với spec CLI: keychain của hệ điều hành được thay bằng `password_command`, theo cách credential helper của git và kubectl. Lý do: keychain cần module native, phá binary đơn Node SEA; `password_command` dùng được với 1Password, Vault, `pass`, AWS Secrets Manager mà không thêm phụ thuộc. Lệnh chạy với trần 10 giây, lấy dòng đầu của stdout, không bao giờ ghi ra log. Thứ tự ưu tiên: `--password-stdin`, rồi `OCHO_PASSWORD`, rồi `password_command`.

## Fixture và CI

Mười hai broker (3 phiên bản × 4 biến thể nguồn), mỗi ca chạy trong vhost riêng của nó, nên toàn bộ ma trận chạy song song trên 12 container thay vì dựng broker cho từng ca.

**Cấu trúc một luật.**

```
fixtures/T2/
  fail-missing-ae/          mẫu lỗi
    definitions.json        nạp vào vhost tên trùng tên ca
    traffic.ts              publish 50 message sai routing key, không mandatory
    ocho.yaml               tuỳ chọn: dung sai, miễn trừ, services
    expected.full.json
    expected.nostats.json
    expected.noprom.json
    expected.listonly.json
  near-ae-via-policy/       mẫu gần giống
  anti-loose-waived/        mẫu phản-canon
```

`expected.*.json` là tập các bộ (luật, đối tượng, kết quả, mức). Harness so tập hợp: thiếu là hỏng recall, thừa là hỏng precision, sai mức cũng là hỏng.

**Bốn biến thể nguồn** dựng bằng cấu hình broker, không bằng giả lập phía CLI, để test chạm đúng hành vi thật:

| Biến thể | Cấu hình |
| --- | --- |
| `full` | Mặc định, bật plugin Prometheus, `collect_statistics_interval = 1000` để thống kê kịp cập nhật |
| `nostats` | Thêm `management_agent.disable_metrics_collector = true` |
| `noprom` | Tắt plugin Prometheus |
| `listonly` | Cả hai |

**Harness** (`tools/run-matrix.ts`) dùng user quản trị riêng của nó để nạp definitions và chạy `traffic.ts`, chờ 2 chu kỳ thống kê, rồi chạy `ocho doctor --json --vhost <ca>` bằng user `monitoring`. CLI không bao giờ thấy user quản trị của harness, nên GC1 được kiểm ở mọi lần chạy.

Ngoại lệ: bộ đếm unroutable là bộ đếm toàn broker, không tách được theo vhost. Các ca T2 dựa vào bộ đếm chạy trên broker riêng dựng mới, để con số khớp chính xác.

**Ba tầng CI.**

| Tầng | Khi nào | Chạy gì | Trần thời gian |
| --- | --- | --- | --- |
| Commit | Mỗi push | Luật trên ảnh chụp, snapshot đầu ra, test kiểu, ma trận 4.2 `full` | 5 phút |
| Đêm | Mỗi ngày | Ma trận 12 broker, broker 10.000 queue, gây lỗi bằng Toxiproxy | 30 phút |
| Phát hành | Mỗi tag | Như đêm, cộng nhật ký chạy tay trên Amazon MQ 3.13 đính kèm release | Không trần; một người ký |

Một ca `fail` mới chỉ được merge khi đi kèm ít nhất một mẫu gần giống của cùng luật. Quy tắc này chặn việc thêm luật nhạy quá mức, vốn là cách bẻ chỉ số recall.
